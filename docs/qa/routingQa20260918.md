## 실제 화면에서 재현한 문제

### ROUTE-F01 · P2 · 완료 기록에서 돌아가면 진행 중 탭으로 이동

- 시작: 메뉴의 여행 기록 → `/record?tab=completed` → 완료된 광주 여행 → `/record/25`.
- 조작: 상세 화면의 상단 ‘이전 화면으로 이동’.
- 기대: 출발한 완료 목록으로 돌아가 목록 맥락 유지.
- 실제: `/record`로 이동하고 기본 탭 ‘진행 중’ 및 ‘아직 탐험 중인 코스가 없습니다’ 표시.
- 근거: `features/record/components/RecordDetail.tsx:70`의 `backHref="/record"`; `app/record/page.tsx`의 기본 탭은 `ongoing`.
- 수정 방향: 완료 기록 상세의 복귀 경로에 완료 탭을 보존한다.

### ROUTE-F02 · P2 · 홈에서 소개를 열었다 돌아오면 장소 선택으로 이동

- 시작: 기록 화면의 홈 버튼 → `/?home=1` → 메뉴 → 서비스 소개 `/about`.
- 조작: 소개 화면의 상단 ‘이전 화면으로 이동’.
- 기대: 소개를 연 홈으로 복귀.
- 실제: `/`를 거쳐 `/places`로 자동 이동. ‘광주에 얼마나 머무르나요?’ 표시.
- 근거: `app/about/page.tsx:38`의 `backHref="/"`; `app/page.tsx`는 `home=1`일 때만 로그인 사용자의 자동 분기를 건너뛴다.
- 같은 패턴: `app/course/page.tsx:37`에도 `backHref="/"`가 있다. 내 코스 화면에서의 재현은 미실행.
- 수정 방향: 명시적 홈 이동과 초기 접속 시 자동 복귀의 URL 규칙을 일치시킨다.

### ROUTE-F03 · P1 · 잘못된 코스·기록 주소에서 복귀 경로가 없음

- 실행: `/explore/qa-missing-course`, `/explore/999999999`, `/record/999999999` 직접 접속.
- 실제: 앞의 두 경로는 ‘코스를 불러오지 못했어요.’, 마지막 경로는 ‘여행 기록을 찾을 수 없어요.’만 표시. 앱의 홈·뒤로가기·재시도 컨트롤이 없다.
- 비교: 존재하지 않는 정적 경로 `/qa-missing-page`에는 정상적으로 404 안내와 ‘홈으로 돌아가기’ 링크가 있다.
- 기대: 명세 6.1.1·6.2에 따라 리소스 오류를 구분하고 복귀 경로를 제공한다. 유효하지 않은 문자열 ID와 미존재 숫자 ID도 구분해 검사한다.
- 근거: `app/explore/[courseId]/page.tsx:128`, `app/record/[recordId]/page.tsx`의 `!summary` 분기. 방문 상세의 `!visit` 분기도 같은 형태이나 이번에 직접 실행하지 않았다.
- 한계: 응답 HTTP 코드를 직접 캡처하지 않았으므로 이번 실행의 모든 오류를 HTTP 404로 단정하지 않는다. 화면에 복귀 동작이 없다는 것은 재현했다.
- 수정 방향: 오류 종류에 맞는 안내와 홈 복귀를 제공하고, 일시적 오류에는 실패한 조회 재시도를 제공한다.

### ROUTE-F04 · P1 · 완료한 코스에서도 시작·확정·수정 경로가 열림

- 사전 확인: `/record?tab=completed`에 QA 여행이 표시되고 `/record/25`에 완료 일시·방문 기록이 있다.
- 실행: 대응 코스 `/course/35?from=hub` 직접 접속 → 코스 일정 보기 → 직접 수정.
- 실제: 코스 화면에 ‘탐험 시작’·‘코스 다시 설계’가 표시된다. 상세에는 ‘이 코스 사용’·‘AI로 다듬기’·‘직접 수정’이 표시되고, `/course/35/edit?mode=manual&from=hub`에서 순서 편집 UI와 ‘수정 완료’ 버튼까지 열린다.
- 기대: 확정 코스는 수정할 수 없고, 이미 완료한 탐험을 신규 시작 대상으로 안내하지 않아야 한다.
- 근거: `app/course/[courseId]/page.tsx:154`는 Course의 `CONFIRMED`만 확인한다. `app/course/[courseId]/detail/page.tsx:110`은 확정·편집 콜백을 항상 전달하고, `app/course/[courseId]/edit/page.tsx:800`은 상태 가드 없이 편집기를 렌더한다.
- 한계: 시작·확정·저장 요청은 실행하지 않았다. 서버에서 실제 변경을 허용한다고 주장하는 결함이 아니라, 수행할 수 없는 작업으로 유도하는 화면·라우트 결함이다.
- 수정 방향: 코스의 DRAFT/CONFIRMED와 탐험의 BEFORE/ONGOING/COMPLETED를 함께 판단하고, 버튼과 직접 URL 진입에 같은 규칙을 적용한다.

## 코드 대조에서 확인한 추가 위험 — 실제 조건 재현 필요

### ROUTE-C01 · P1 · BEFORE 탐험을 홈에서 복구하지 못함

- `app/page.tsx:65`는 ONGOING 목록만 조회한다. 시작 전 탐험만 있다면 빈 목록을 받고 `:89`에서 `/places`로 보낸다.
- 명세 1.1.1은 BEFORE를 코스 미리보기로 보내도록 정한다.
- BE `ExplorationService.getExplorations`는 BEFORE 목록 요청을 거부하므로 FE에서 쿼리 문자열만 바꿔 해결할 수 없다. 세션 판별 API 상세도 미확정이다.
- 재검사: 코스 확정 직후 시작하지 않은 계정으로 `/` 접속·새로고침. 같은 계정을 다른 기기에서 로그인한 경우도 확인.

### ROUTE-C02 · P1 · 홈의 상태 조회 실패를 코스 없음으로 처리

- `app/page.tsx:85`는 `isCourseCheckError`일 때 `ongoingCourse`를 undefined로 두고 `/places`로 보낸다.
- 명세 1.1.1·6.2는 판별 실패 안내와 재시도를 요구한다. 실패를 정상 빈 상태로 대체하면 원래 진행하던 탐험이 없는 것처럼 보인다.
- 재검사: 테스트 환경에서 목록 조회에 네트워크 오류·5xx를 주고, 홈 유지·재시도·성공 후 올바른 복귀를 확인.

### ROUTE-C03 · P1 · 시작 전 초대 합류도 미리보기를 건너뛰고 지도 진입

- `app/explore/[courseId]/page.tsx:86`과 각 합류 성공 콜백은 상태 확인 없이 `/explore/{courseId}/map`으로 이동한다.
- 지도에는 탐험 시작 동작이 없다. `useStartExplorationMutation`의 호출자는 `app/course/[courseId]/page.tsx`뿐이다.
- 따라서 BEFORE에 합류한 팀원은 정상 초대 경로에서 시작 전 미리보기·탐험 시작 동작으로 이어지지 않는다. 지도 내부의 팀원·방문 기능도 상태별로 추가 확인이 필요하다.
- 재검사: A가 확정만 한 코스에 B가 합류 → BEFORE 미리보기와 팀원 시작 버튼 확인 → B 시작 → 양쪽 ONGOING 지도 확인.

### ROUTE-C04 · P1 · URL의 코스와 전역 탐험 ID가 다를 수 있음

- 지도 `app/explore/[courseId]/map/page.tsx:50`과 탐험 일정 `app/explore/[courseId]/course/page.tsx:31`은 전역 `sessionStore.explorationId`를 사용한다. 코스는 URL의 courseId로 별도 조회한다.
- 세션 ID가 없으면 지도는 ‘다시 합류해 주세요’만 표시한다. 다른 코스의 ID가 남아 있으면 코스 표시와 팀·방문·완료 요청의 대상 탐험이 달라질 수 있다.
- `DuplicateExplorationState.tsx:37`의 기존 지도 이동도 조회한 ID를 복구하지 않고 지도 URL만 연다.
- 코스 시작도 `app/course/[courseId]/page.tsx:85`에서 응답에 값이 없으면 전역 ID를 사용한다. FE 타입에 선언한 `explorationId`는 현재 BE의 `CourseDetailResponse`에 없다.
- BE에는 코스별 탐험 ID 조회 `GET /api/v1/courses/{courseId}/exploration`이 있으며, FE endpoint 상수만 존재하고 해당 조회 호출은 검색에서 확인되지 않았다.
- 재검사: 동일 계정의 코스 X/Y, 전역 ID 없음·X·Y 각각에서 Y 지도·일정 직접 접속. 조회와 모든 행동 대상이 Y의 탐험인지 확인한다. 저장·완료 행동은 통제된 테스트 데이터로 검증한다.

### ROUTE-C05 · P1 · 기존 탐험 복귀가 공유 링크 만료에 묶임

- 홈 `app/page.tsx:89`와 진행 중 기록 `app/record/page.tsx:171`은 `/explore/{courseId}`를 사용한다. `stage=ongoing` 쿼리도 초대 페이지에서 읽지 않는다.
- 이 페이지는 공유 코스 조회 후 join을 호출한다. 현재 로컬 BE의 `CourseService.java:606`과 `ExplorationService.join`은 공유 만료를 검사한다. 이미 참여한 사용자도 이 경로를 거친다.
- 지도 직접 접속 역시 같은 `getCourseForView` 조회를 사용하므로 URL만 `/map`으로 바꿔서는 전체 해결이 되지 않는다.
- 재검사: 공유 기한만 만료되고 탐험은 ONGOING인 기존 참여자의 홈·기록·직접 지도 복귀. 새 초대자의 만료 거부와 기존 참여자의 탐험 재진입을 구분한다.
- 한계: 운영에서 시간·데이터를 변경하지 않았고, 배포 BE 버전도 확인하지 않았다. 현재 로컬 FE·BE 코드 조합에서 확인한 위험이다.

### ROUTE-C06 · P1 · 합류 요청의 일반 오류가 무한 대기처럼 보임

- 초대 페이지는 join의 특정 409·410만 처리한다. 그 외 오류는 로그인 상태 분기 `app/explore/[courseId]/page.tsx:165`로 내려가 ‘탐험에 합류하고 있어요…’를 계속 표시한다.
- 재검사: 코스 조회는 성공시키고 join만 5xx·네트워크 오류로 실패시킨다. 대기 종료·재시도·홈 복귀를 확인한다.
- 관련 확인: 코스 GET의 410은 joinError 처리에 도달하지 못해 F03의 일반 오류 화면으로 끝난다. 만료 링크 전용 안내도 조회 오류 단계부터 검사해야 한다.

## 권장 수정·재검사 순서와 남은 범위

1. 탐험 ID 복구와 상태별 진입(C01·C03·C04·F04).
2. 기존 참여자의 만료 후 복귀(C05), 오류에서 빠져나오기(F03·C02·C06).
3. 명시적 홈과 기록 탭 복귀 일치(F01·F02).
4. 위 항목 수정 후 신규 사용자·BEFORE·ONGOING·COMPLETED·비참여자 각각으로 직접 진입/내부 링크/새로고침/브라우저 뒤로가기를 반복한다.

이번에는 기존 QA 세션의 조회·화면 이동만 실행했다. 신규 사용자, BEFORE/ONGOING 준비, 두 사용자 동시 화면, 만료·네트워크 오류 주입, 실제 모바일, 로그인 전환, 편집 데이터가 있는 이탈은 미실행이다. 앱 코드를 변경하지 않은 수동 QA이므로 전체 자동 테스트·lint·빌드는 실행하지 않았다. 브라우저 관찰을 해당 검사들의 통과로 대신하지 않는다.
