## 1. 목적과 판정 원칙

심사위원의 첫 접속 → 성향 검사·코스 생성 → 팀 합류 → 가상 위치 체험 → 방문·완료 → 여행 기록까지 실제 FE·BE로 검증한다. 사용자 조작, API 응답, 저장 결과, 다른 팀원 화면과 새로고침 후 복구가 일치해야 한다. 화면만 정상인 경우나 mock 응답으로 확인한 경우를 실제 통합 성공으로 판정하지 않는다.

체험 기능은 제출 서비스의 핵심 검증 경로다. 체험으로 방문·완료 기록이 생성되는 것 자체는 결함으로 판정하지 않는다. 체험 기록의 최종 저장·구분·보존 정책은 후순위 논의로 유지한다. 실제 GPS 수신·현장 방문 검증은 별도 항목이며, 미검증이면 그 한계를 표시한다. 상용 운영을 전제로 한 대규모 부하·장기 보존·운영 데이터 분리 체계를 이번 제출의 필수 조건으로 추가하지 않는다. 계정 간 접근 권한, 비밀값 노출, 제출 데이터의 일관성은 계속 확인한다.

제품 요구사항은 기능 명세를 기준으로 삼는다. 현재 구현이 다르다는 이유로 기대 결과를 구현에 맞춰 바꾸지 않는다. `mvp.md`의 백엔드 테스트 이력은 참고 자료이며 이번 FE·BE 연동의 통과 증거가 아니다. 미구현 기능도 범위에서 제외하지 않고 실행 차단 사유를 기록한다.

### 우선순위와 검증 방식

| 구분 | 의미 |
| --- | --- |
| P0 | 제출 URL 접속, 핵심 심사 여정·체험·팀 동기화·기록을 막는 문제, 계정 간 권한 오류·비밀값 노출·데이터 불일치. 우선 실행 |

| P2 | 표현·편의·시각적 동작 |
| 통합 | 실제 FE·BE 연결. UI 조작과 API 결과·재조회·다른 사용자 화면으로 검증 |
| UI | 브라우저·기기 동작 확인. mock 사용 여부를 기록하고 실제 연동 결과와 구분 |

통합 테스트의 서버 상태는 우선 조회 API로 확인한다. 서버 내부 롤백·외부 호출 횟수·좌표 미저장 등 화면에서 확인할 수 없는 항목은 테스트 로그·백엔드 테스트 또는 허용된 테스트 DB 확인 증거가 필요하다. API 테스트만 통과해도 대응 UI가 미검증이면 통합 통과로 승격하지 않는다.

### 제출 필수 검사

아래 SUB 항목을 제출 관문의 기준으로 사용한다. 기존 기능별 케이스는 상세 검사 목록으로 유지하며, 미실행 항목은 결과에 남긴다. 모든 항목의 현재 상태는 미실행이며, 기존 로그인 QA 등 일부 증거는 해당 버전·범위에만 재사용한다.

| ID | 심사 상황과 검사 | 통과 기준 |
| --- | --- | --- |
| SUB-01 | 제출 URL을 로그인 이력 없는 새 브라우저에서 직접 열기 | 개발 도구·사전 저장 정보 없이 진입 가능. 페이지·지도·이미지·API 연결이 정상이고 서버가 심사 기간에 접근 가능한지 확인 |
| SUB-02 | 성향 검사 → 등록 → 일정·장소 선택 → 코스 생성·수정·확정 | 다음 단계가 막히지 않고 선택한 장소·일정이 보존됨. 응답 지연에는 로딩·실패 안내가 있으며 실제 대기 시간을 기록 |
| SUB-03 | 광주 밖·위치 권한 거부·위치 취득 실패에서 체험 진입 → 이동·방문 → 완료·기록 | 광주 방문이나 브라우저 좌표 조작 없이 체험 가능. 실제 API와 방문·진행률·완료·기록 화면이 일치하고 실패를 성공으로 표시하지 않음 |
| SUB-04 | 별도 브라우저/기기로 공유 링크 합류 → 탐험 시작 → 방문·완료 | 같은 팀·탐험으로 연결되고 두 화면이 갱신됨. 다른 탐험·계정의 데이터가 섞이지 않음 |
| SUB-05 | 직접 URL 접속·새로고침·뒤로가기·재로그인·잘못된 링크 | 해당 상태의 화면으로 복구되며 오류에서 돌아갈 수 있음. 초대 링크는 심사 기간 중 만료 가능성과 새 링크 준비 방법을 확인 |
| SUB-06 | 시연 완료 뒤 새 계정·새 여행으로 같은 흐름 반복 | 이전 세션·완료 탐험 때문에 막히지 않음. 발표용 시작 데이터와 재시연 절차를 기록하고 실행 확인 |
| SUB-07 | 실제 제출 FE·BE 버전과 외부 연동으로 최종 확인 | CORS·WebSocket·지도·AI·사진 등 제출 기능의 실제 설정에서 검증. 사용한 fallback을 명시하고 로컬에서 비활성화한 연동을 통과로 간주하지 않음 |
| SUB-08 | 발표 장비와 모바일에서 버튼·지도·입력·기록·공유 확인 | 핵심 조작이 가려지거나 잘리지 않음. 발표자가 도움 없이 진행 가능한 절차로 리허설하며 심사위원의 독립 체험도 확인 |

검증은 로컬에서 재현·수정한 뒤 제출 URL에서 다시 수행한다. 별도 상용 서비스나 별도 시연 서버 구축을 전제로 하지 않는다. 최종 제출 URL·심사 기간·대상 기기는 확정값을 실행 회차 정보에 적고, 아직 정하지 않았다면 미확정으로 남긴다.

### 계정·상태·데이터

- 서로 저장소와 로그인 상태가 분리된 브라우저 프로필 또는 기기를 사용한다. 같은 프로필의 탭 두 개를 다른 사용자로 간주하지 않는다.
- A: 코스 생성자이자 최초 OWNER. B: 일반 팀원. C: B와 닉네임은 같고 실제 사용자는 다른 팀원. D: 해당 탐험 참여 이력이 없는 사용자.
- 각 테스트의 시작 상태를 독립적으로 준비한다. `DRAFT`, `BEFORE`, `ONGOING`, `COMPLETED` 코스·탐험과 `ACTIVE`, `LEFT`, `COMPLETED` 참여자를 구분한다.
- 기본 탐험은 당일 코스 P1·P2·P3과 코스 외 주변 장소 N1을 사용한다. 개인 방문 테스트는 마지막 코스 장소가 아닌 P1에서 시작한다.
- 추천은 충분한 유형별 후보, 후보 부족, 20개 미만 최종 회차, 0개를 재현할 데이터가 필요하다. 예상 성향 점수를 계산할 수 있는 고정 질문·답변도 준비한다.
- GPS는 허용·거부, 정확도 49.9/50/50.1m, 거리 99.9/100/100.1m, 이동 9.9/10/10.1m를 검증할 입력을 준비한다. 거리 경계는 서버와 동일한 좌표 정밀도·거리 계산 기준으로 사전 계산하고 실제 서버 판정값을 기록한다.
- 기간 최소 선택 수는 당일 3개, 1박 2일 5개, 2박 3일 7개, 그 이상 20개다. 각 최소값 전후 데이터를 준비한다.
- 사진은 정상 JPEG·PNG·WebP, 미지원 형식, 크기 상한 전후 파일을 준비한다. 정확한 10MB 바이트 기준은 실행 전 API 계약에서 확인한다.
- 링크·임시 응답 만료와 타임아웃은 테스트 환경의 시계·고정 데이터·지연 응답으로 재현한다. 실제 3일을 기다리거나 운영 데이터의 시각을 바꾸지 않는다.
- 실시간은 `/ws`의 인증 STOMP와 탐험별 `/events`, `/visits`, `/locations` 채널을 관찰한다. 구독자·발행자 계정을 기록한다.
- 외부 연동 실패는 테스트 환경에서만 통제한다. FE만 응답을 대체한 결과와 실제 BE의 fallback 결과를 구분한다.

권장 기기 조합은 데스크톱 브라우저, Android Chrome, iOS Safari다. 실제 GPS·카메라/사진 선택·저장·시스템 공유는 모바일 실기기에서 확인하고, 미확인 환경은 그대로 미실행으로 남긴다.

## 3. 핵심 종단 시나리오

아래 8개는 상세 통합 시나리오다. E2E-01~04와 E2E-08의 심사 중 재접속·복구를 우선 확인하고 E2E-05~07은 추가 기능 검사로 진행한다. 제출 판정은 SUB-01~08을 따른다. 각 여정의 마지막에 조회 API와 새로고침으로 저장 상태를 확인한다. 오류 세부 분기는 4~9절에서 별도로 실행한다.

### E2E-01 신규 사용자 혼자 여행 완료

- 명세: 1.1.1~1.3.1, 2.1.1~2.3.2, 3.1.0~3.3.3, 4.2.4, 4.3.3, 5.1.2, 5.2.1~5.2.2.
- 사전 조건: 새 브라우저 저장소, 새 사용자 A, 추천 가능한 장소 3곳 이상. 제출 필수 회차는 가상 광주 위치 체험을 사용하고 실제 GPS 회차는 별도로 기록한다.
- 단계: 서비스 시작 → 기본 성향 검사 → 닉네임 등록·식별코드 확인 → 당일 일정 선택 → 회차를 끝까지 처리해 3곳 이상 좋아요 확정 → AI 코스 생성 → 코스 확정 → 탐험 시작 → 각 코스 장소에 유효한 위치로 방문 인증 → 마지막 방문의 사진·메모 저장 → 여행 기록·밝힌 지도 조회.
- 기대 결과: 성향·일정·선택 장소가 단계 간 유지된다. 선택한 장소가 누락·중복 없이 코스에 포함된다. 마지막 코스 장소 방문으로 자동 완료된다. 완료 직후에도 작성자는 마지막 방문 기록을 저장할 수 있다. 완료 코스·방문 기록·밝힌 지도가 일치한다.

### E2E-02 신규 팀원 합류와 팀원의 탐험 시작

- 명세: 3.3.2~3.3.3, 4.1.1~4.2.4, 4.3.2.
- 사전 조건: A의 확정 코스와 BEFORE 탐험, 유효한 공유 링크, B는 세션 없음.
- 단계: A가 링크 생성 → B가 독립 브라우저에서 접속 → 성향 검사 없이 닉네임 등록·식별코드 발급·합류 → A/B 팀 목록 조회 → B가 탐험 시작.
- 기대 결과: B가 한 번만 합류하고 양쪽 팀 목록이 일치한다. BEFORE에는 방문·주변 추천·내 위치 기능이 없다. MEMBER인 B도 시작할 수 있고 A 화면도 ONGOING으로 갱신된다.

### E2E-03 기존 계정 복구와 탐험 복귀

- 명세: 1.1.1, 1.1.3, 4.1.1, 5.1.1, 5.2.1.
- 사전 조건: 방문 기록이 있는 A의 ONGOING 탐험, 로그인 정보 보유.
- 단계: 로그아웃 → 닉네임·식별코드 로그인 → 기존 탐험 복귀 → 같은 공유 링크 재진입 → 새로고침.
- 기대 결과: 기존 사용자·참여자로 복구한다. 팀 인원·방문 기록이 중복되지 않는다. 진행률·본인 인증 여부·기존 사진·메모가 보존된다.

### E2E-04 개인 인증과 팀 진행률 분리

- 명세: 4.3.2~4.3.4, 5.1.2, 5.2.1~5.2.2.
- 사전 조건: A/B ACTIVE, ONGOING, P1·P2·P3 미방문, 위치 입력 정확도 50m 이하·각 장소 거리 100m 이하. 합성 좌표로 API 계약을 검사할 수 있으며 실제 GPS 수신 검사와 구분한다.
- 단계: A가 P1 인증 → B가 P1 인증 → A가 P1 재인증 시도 → 양쪽 새로고침 → A가 P2, B가 P3 인증.
- 기대 결과: 첫 인증 후 팀 1/3·개인 A=1/B=0. B 인증 후 팀은 1/3·개인 A=1/B=1, P1 Visit은 2건이다. A 재인증은 거부되고 값이 변하지 않는다. 새로고침 후 동일하다. P3 인증으로 팀 3/3·자동 완료이며, 모든 팀원이 모든 장소를 인증할 필요는 없다.

### E2E-05 주변 장소 방문과 기록

- 명세: 4.4.1~4.4.2, 4.3.3, 5.2.1~5.2.2.
- 사전 조건: ONGOING, 광주 내 좌표(체험 또는 실제 GPS, 입력 방식 기록), 코스 외 N1이 1km 내 존재.
- 단계: 주변 장소 더보기 → N1 상세 → 인증 반경 내에서 방문 → 사진·메모 저장 → 팀 방문 기록·밝힌 지도·코스 진행률 조회.
- 기대 결과: 직접 클릭할 때만 추천한다. N1은 방문 기록과 지도에 포함되고 `coursePlaceId=null`이다. 코스 진행률의 분자·분모는 변하지 않는다.

### E2E-06 기존 탐험 이탈 후 새 탐험 합류

- 명세: 4.1.1, 6.4.1, 5.1.1~5.2.1.
- 사전 조건: A는 탐험 X에 ACTIVE, X에 방문·사진 기록 존재, 다른 코스 Y 링크 유효.
- 단계: Y 링크 합류 → 중복 참여 안내 → 기존 지도 이동 분기 확인 → 다시 Y 합류 → 나가고 참여 선택 → 확인 취소 → 다시 실행·확인 승인.
- 기대 결과: 취소까지는 X 참여 유지. 승인 후 X leave 성공 다음 Y join 순서로 요청한다. X 기록을 보존하고 활성 참여는 Y 하나다. X 이탈 뒤 Y 합류 실패 분기는 TEAM-10에서 별도 검증한다.

### E2E-07 소유권 승계 후 조기 완료

- 명세: 6.4.1, 4.3.2, 5.1.2.
- 사전 조건: ONGOING, A OWNER, B가 C보다 먼저 합류, 미방문 코스 장소 존재.
- 단계: A 이탈 → B/C 팀 목록·권한 확인 → A 재합류 → C 조기 완료 시도 → B가 조기 완료 확인 모달 취소 후 다시 승인.
- 기대 결과: B가 OWNER가 되고 A 재합류로 권한이 돌아가지 않는다. C 완료 요청은 거부된다. B 취소 시 상태 유지, 승인 시 진행률을 부풀리지 않고 COMPLETED 전환한다. 기존 기록·사진을 보존하고 현재 팀원 화면에 완료를 전파한다.

### E2E-08 새로고침·연결 단절 후 복구

- 명세: 2.1.2, 2.2.2~2.2.3, 4.3.2~4.3.3, 5.2.1.
- 사전 조건: 선택 단계의 A와 별도 ONGOING 탐험의 A/B 데이터를 각각 준비.
- 단계: 완료된 추천 회차와 미전송 반응이 있는 상태에서 새로고침 → 선택 상태 확인. 탐험에서는 B 연결 끊기 → A 방문 인증 → B 재접속 → 팀·방문 조회 결과 확인 → 중복 이벤트 입력.
- 기대 결과: 저장 반응은 서버 결과와 일치하며 미전송 반응은 합의된 로컬 복구 규칙을 따른다(Q-07). 재접속 후 HTTP 조회로 진행률·방문 핀·팀원을 복구한다. 중복 이벤트로 인원·방문 수가 증가하지 않는다. 과거 위치 좌표의 replay를 기대하지 않는다.

- 미실행: 아직 실행하지 않음. 현재 모든 케이스의 상태.

```text
영향 범위 / 임시 회피 방법:
수정 리비전 / 재검증 결과:
```

제출 QA 완료 기준은 실제 제출 URL·대상 버전에서 SUB-01~08 통과, 핵심 흐름을 막는 P0와 계정 간 권한·데이터 일관성 문제 해결, 남은 P1·미실행·정책 보류 항목과 영향 명시다. 체험으로 기록이 생긴다는 사실이나 현장 GPS 미검증만으로 제출 실패로 판정하지 않으며, 현장 GPS가 검증됐다고 표현하지도 않는다. mock 통과만 있는 항목, 미실행·차단 항목은 통합 통과율의 통과 건수에 넣지 않는다. 실행 건수는 케이스 행 수가 아니라 변형·환경별 결과표 행 수로 센다. 코드·환경 변경 후 영향받은 케이스와 핵심 여정을 재검증한다.

## 13. 권장 실행 순서

1. 환경·제출 조건 확인: 회차 정보, 제출 URL·기간·장비, 독립 사용자, 실제 API 연결을 기록한다.
2. 로컬에서 SUB-02~05: 코스 생성·합류·체험 완료·기록·라우팅을 먼저 검사하고 결함을 수정한다.
3. SUB-06: 새 계정·새 여행으로 재시연하고 시작 조건·복구 절차를 기록한다.
4. SUB-01·07·08: 실제 제출 URL·외부 연동·발표 장비·모바일에서 확인한다. 로컬 성공만으로 제출 준비 완료라고 판단하지 않는다.
5. 제출 환경에서 SUB-01~08 전체 리허설을 수행하고 E2E-05~07·상세 경계 검사로 범위를 넓힌다. 실제 GPS 회차는 별도 기록한다.
6. 실패·차단·미실행·보류를 결과표에 남기고 수정된 범위와 연관 핵심 여정을 재검증한다.

이 문서를 추가한 시점에는 테스트 실행, 앱 코드 변경, 백엔드 수정, 커밋·푸시를 수행하지 않았다.
