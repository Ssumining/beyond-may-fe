## 생성한 계정과 상태 데이터

한 계정의 활성 탐험 중복 참여 제한 때문에 상태별로 계정을 분리했다. 아래 닉네임은 로컬 QA용 가상 계정이다. 모든 코스는 확정 상태이며 여행 일정은 2026-09-20 당일치기다.

| 상태              | 소유자 (사용자 ID) | 팀원 (사용자 ID) | 코스 / 탐험 ID | 방문               |
| ----------------- | ------------------ | ---------------- | -------------- | ------------------ |
| 시작 전 `BEFORE`  | `Q919BOwner` (1)   | `Q919BMate` (2)  | 1 / 1          | 0/3                |
| 진행 중 `ONGOING` | `Q919OOwner` (3)   | `Q919OMate` (4)  | 2 / 2          | 1/3, 방문 ID 1     |
| 완료 `COMPLETED`  | `Q919COwner` (5)   | `Q919CMate` (6)  | 3 / 3          | 3/3, 방문 ID 2·3·4 |

기존 회원가입 → 추천·장소 선택 → 코스 생성·확정 → 팀원 합류 API로 생성했다. 진행·완료 데이터는 시작 API와 방문 API로 준비했다. 방문은 장소 좌표를 사용한 **합성 입력**이며 실제 GPS 성공 증거가 아니다. 사진·메모는 추가하지 않았다.

계정 6개 모두 로그인 API 성공을 확인했고, 확인용 로그인 세션은 로그아웃했다. 로그인 식별코드·토큰은 문서나 출력에 남기지 않았다. 사용자는 로컬 DB 클라이언트에서 아래 조회 결과를 직접 확인해 화면의 ‘여행 이어가기’에 닉네임과 식별코드를 입력한다. 결과를 QA 보고서에 복사하지 않는다.

```sql
SELECT nickname, identification_code
FROM users
WHERE nickname IN (
  'Q919BOwner', 'Q919BMate', 'Q919OOwner',
  'Q919OMate', 'Q919COwner', 'Q919CMate'
)
ORDER BY user_id;
```

## 재현 시작 조건을 기록하는 방법

각 검사에 **환경·계정/역할·서버 상태·브라우저 상태·시작 주소·조작·기대 결과**를 적는다. 기대 결과와 실제 결과는 구분한다. 다음 예시는 앞으로 실행할 검사 절차이며 이번에 통과한 결과가 아니다.

| 항목               | 예: 시작 전 탐험의 홈 복귀 검사                                                  |
| ------------------ | -------------------------------------------------------------------------------- |
| 환경               | 위 FE·BE 버전, 로컬 API, mock 꺼짐                                               |
| 계정·역할          | `Q919BOwner`, 탐험 1의 소유자                                                    |
| 서버 시작 상태     | 코스 1 확정, 탐험 1 `BEFORE`, 참여자 2명, 방문 0개                               |
| 브라우저 시작 상태 | 로컬 QA 전용 새 브라우저 프로필에서 로그인. 이전 운영 로그인·여행 선택 정보 없음 |
| 시작 주소          | `http://localhost:3000/` — `?home=1` 없이 접속                                   |
| 조작               | 새 탭으로 직접 접속 → 최종 화면 기록 → 새로고침 후 화면 기록                     |
| 기대 결과          | 시작 전 탐험을 복구하고 미리보기·시작 동작으로 이어짐                            |
| 실제 결과          | 미실행. 실행 후 최종 URL·화면·오류 및 판정을 추가                                |

기존 저장 상태에서 재접속하는 검사라면 새 프로필 대신 ‘로그인·여행 선택 상태 유지’라고 명시한다. 시작 URL의 쿼리도 그대로 적는다. 이 앱은 `/?home=1`과 `/`의 자동 이동 조건이 다르다. 두 사용자 검사는 같은 `http://localhost:3000`을 별도 브라우저 프로필에서 열어 로그인 상태를 분리한다.

시작·방문·완료 검사를 하면 위 데이터의 상태가 달라진다. 같은 검사를 반복하기 전 상태를 다시 조회하고 필요하면 새 QA 세트를 만든다. 완료 데이터를 강제로 되돌리거나 기존 데이터를 삭제하지 않는다. 초대 링크는 생성 3일 후 만료될 수 있으므로 유효 링크 검사 전 만료 시각을 확인한다.

## 다시 실행하는 명령

기존 서버가 실행 중이면 중복 실행하지 않는다. 아래 명령은 각 저장소의 별도 PowerShell 터미널에서 실행한다. 필요한 로컬 DB 인증 설정은 기존 환경 파일을 프로그램이 로드한다.

백엔드 저장소:

```powershell
$env:DB_NAME='beyond_may_qa'
$env:DB_PORT='127.0.0.1:15432'
docker compose -p beyond-may-qa up -d postgres
.\gradlew.bat bootRun --args="--server.address=127.0.0.1 --server.port=8080 --spring.datasource.url=jdbc:postgresql://127.0.0.1:15432/beyond_may_qa --groq.api-key= --tour-api.service-key= --visit-photo.bucket="
```

프론트엔드 저장소:

```powershell
$env:NEXT_PUBLIC_API_MOCKING='off'
$env:NEXT_PUBLIC_API_BASE_URL='http://localhost:8080'
$env:NEXT_PUBLIC_SOCKET_URL='ws://localhost:8080/ws'
npm.cmd run dev -- --hostname 127.0.0.1 --port 3000
```

브라우저에서는 `http://localhost:3000`으로 접속한다. `127.0.0.1:3000`은 허용된 CORS origin과 다르다. 이전 운영 로그인으로 로컬에 접속하면 세션 만료 안내가 나올 수 있으며 로컬 QA 계정으로 다시 로그인한다.
