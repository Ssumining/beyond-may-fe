# QA 문제 해결 순서

- 작성일: 2026-09-18
- 목적: 공모전 제출 URL에서 심사위원이 핵심 기능을 직접 체험하고 발표자가 반복 시연할 수 있도록, 전체 QA와 라우팅 QA 문제를 원인·심사 영향·의존관계에 따라 해결한다.
- 문서 성격: 대화에서 정한 작업 순서와 완료 기준을 정리한 QA 작업 안내다. 구현 spec이나 implementation ticket은 아니며, 미확정 API·권한 정책을 확정하거나 구현 완료를 의미하지 않는다.
- 현재 진행 상태: 0번 환경 준비에 이어 **대화에서 정한 1번 로그인·홈 라우팅을 2026-09-19 완료**했다. 상태별 복구와 로그인 메뉴 닫힘을 구현했으며 사용자가 수동 QA 전체 정상 동작을 확인했다. [완료 체크리스트](manualLoginQa20260919.md)와 [환경 기준](localQaBaseline20260919.md)을 참고한다. 전체 회귀 QA와 나머지 문제는 별도 진행한다.
- 우선순위 변경(2026-09-19): 체험 기능은 QA·공모전 시연 목적으로 유지한다. 기존 1번의 체험 기록 정책 논의·수정은 후순위로 보류하고, 다음 작업은 2번 탐험 ID·상태 조회 정리로 한다.

## 작업 순서와 완료 기준

검증 환경을 준비한 뒤 상태 판별과 화면 이동을 먼저 수정한다. 기존 문서·대화의 참조를 유지하기 위해 작업 번호는 바꾸지 않는다. 실행 순서는 0 → 2~7 → 8이며, 기존 1번은 별도 후순위 논의 항목으로 유지한다.

## 체험 기능의 사용 범위와 보류 결정

- 사용 목적은 광주로 이동하지 않고 가상 좌표로 실제 API와 여행 흐름을 확인하는 QA, 공모전 시연·기능 제출이다. 현 체험 기능과 기록 생성 동작을 유지한다.
- 서비스 자체가 공모전 제출용이다. 체험 기능의 핵심 흐름 검증은 지금 진행하고, 기록 정책 재설계만 후순위로 둔다. 체험 기록 생성 자체를 결함으로 간주하거나 상용 운영용 데이터 분리 체계 구축을 제출 선행 조건으로 추가하지 않는다.
- 현재 QA는 [로컬 QA 전용 DB](localQaBaseline20260919.md)에서 수행한다. 합성 좌표로 생성한 방문·완료 기록은 실제 기기 GPS·현장 방문 검증 결과와 구분한다.
- 체험 기록의 최종 저장·표시·보존·구분 정책은 미확정이다. 현 기록 동작을 유지하며 별도 시연 서버나 서버의 체험 구분 필드를 채택한 것으로 해석하지 않는다. 최종 제출 URL·버전·심사 기간은 최종 QA의 실행 조건으로 확인한다.
- 기존의 ‘체험 기능의 실제 기록 생성 차단’은 확정된 구현 목표에서 제외한다. 관련 관찰·증거는 F-04에 보존하고 후순위로 재논의한다. 일반 여행 모드의 GPS·권한·방문 반경 검증 기준은 유지한다.
- 이 보류는 2~7번 진행을 막지 않는다. 8번 회귀 보고에도 미확정 체험 기록 정책을 남기며, 보류를 해결이나 배포 승인으로 취급하지 않는다.

## 의존관계와 작업 묶음

- **0번 준비 후 다음 작업은 2번:** 체험 기능의 기록 정책 논의를 기다리지 않고 탐험 ID·상태 조회 정리부터 진행한다. 기존 1번은 후순위로 보류하며 QA 데이터 삭제는 포함하지 않는다.
- **라우팅의 첫 핵심 묶음은 2~3번:** 코스와 탐험의 대응·상태를 정확히 알아야 화면 진입과 행동을 올바르게 제한할 수 있다.
- **4번은 2번의 조회·권한 계약을 바탕으로 진행:** 이동 주소만 `/map`으로 바꿔도 지도 조회가 공유 만료에 묶여 있으면 복귀 문제가 남는다.
- **5~6번은 각 화면의 오류·복귀 동작 정리:** 모든 수정이 끝날 때까지 검증을 미루지 않고 묶음마다 재검사한다.
- **7~8번은 통합 검증 확대:** 실제 두 사용자와 모바일에서 확인하고 최종 대상 버전으로 회귀 검사를 수행한다.

작은 뒤로가기 문제부터 모두 고친 뒤 상태 처리를 다시 바꾸는 순서를 피한다. 화면마다 코스·탐험 상태를 다르게 판단하는 원인을 먼저 해결해야 다른 진입 경로에서 같은 문제가 반복되지 않는다.

## 2번 착수 전에 확정할 사항

다음은 구현 전에 해결해야 할 결정이며, 이 문서에서 구체적인 API를 새로 확정하지 않는다.

| 결정 | 현재 확인한 제약 | 확정할 내용 |
| --- | --- | --- |
| 홈에서 시작 전 탐험을 찾는 방법 | 완료: `GET /api/v1/courses`와 `GET /api/v1/explorations?status=BEFORE/ONGOING`을 조합한다. | ACTIVE 참여 탐험을 우선하고 초안은 updatedAt DESC, courseId DESC로 선택한다. 홈 범위 구현·사용자 QA 완료. |
| 기존 참여자의 코스 조회 권한 | 현재 조회·재합류 경로가 공유 링크 만료와 연결되어 있다. | 만료 후 기존 참여자의 조회·복귀 방식과 비참여자·이탈자 등 권한 경계. |
| 상태별 허용 화면·행동 | 코스 상태와 탐험 상태를 일부 화면에서 구분하지 않는다. | `DRAFT`·`CONFIRMED`, `BEFORE`·`ONGOING`·`COMPLETED`, 소유자·팀원·비참여자를 함께 고려한 진입·행동 규칙. |

기존 API로 해결할 수 있는 부분부터 사용하고 부족한 계약만 추가한다. API·권한 변경은 영향 범위를 조사하고 관련 제품·API 문서와 검증 범위를 함께 정한다.

## 단계별 검증 방식

1. 문제의 시작 상태와 기대·실제 결과를 재현한다. 코드에서만 발견한 위험은 결함 여부부터 확인한다.
2. 비즈니스 로직·분기가 필요한 수정은 실패하는 테스트 → 통과하는 최소 수정 → 코드 정리 순서로 진행한다.
3. 변경 위험도와 저장소 검증 규칙에 맞는 자동 테스트·품질 검사·빌드를 실행한다. 문서·단순 링크 변경에 형식적인 TDD를 강제하지 않는다.
4. 실제 브라우저에서 원래 재현 절차와 인접 흐름을 검사한다. 버튼 이동뿐 아니라 직접 URL 접속·새로고침·앱 뒤로가기·브라우저 뒤로/앞으로도 확인한다.
5. 사용자 조작 결과가 화면·조회 결과·다른 사용자 화면에 일치하는지 확인한다. API 통과를 UI 통합 통과로 대체하지 않는다.
6. 결과에 대상 버전, 통과·실패·차단·미실행, 증거와 남은 문제를 기록한다.

만료·장애·동시 요청과 상태 변경 검사는 통제된 테스트 환경과 데이터로 수행한다. 실제 모바일 GPS 검증과 합성 좌표 검증은 구분한다. 운영 데이터 변경이나 배포는 이 문서 작성 요청에 포함되지 않는다.
